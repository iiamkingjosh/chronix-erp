Chronix OS — Full System Documentation

A complete internal business management platform built for Chronix Technology Limited

What Was Built

Chronix OS is a full-stack internal enterprise resource planning (ERP) platform built on Next.js 14 (App Router), TypeScript, Tailwind CSS, and Firebase (Authentication + Firestore). It replaces manual spreadsheet workflows across every department with a unified, role-secured, real-time digital workspace.


Every module is connected — invoices link to clients and subscriptions, payroll auto-generates PAYE tax records, audit logs capture every significant action, and push + email notifications keep the right people informed in real time.

Modules Built

Finance

Invoices, Payments, Expenses, P&L Reports, AR/AP Aging, Revenue by Client. Full e-invoicing with server-side PDF generation and email delivery to clients.

CRM

Client directory, Lead pipeline, Follow-up tracking. Full client lifecycle from prospect to active account.

HR

Employee roster, Payroll (with automatic PAYE computation on completion), Leave management, Disciplinary records, Performance notes.

Tax

PAYE with Nigerian tax bands, VAT (7.5%), Withholding Tax, Corporate Income Tax estimation. Export to CSV, Excel, and PDF.

Subscriptions

Track all software, domain, and service subscriptions. Renewal reminders at 60/30/7/1 days. Auto-creates draft invoice at 7-day mark.

Tickets

Internal support ticketing system with priority levels, assignment, SLA tracking, and status management.

Projects

Project management with status tracking, team assignment, milestones, and time tracking integration.

Procurement

Vendor directory, Purchase Order management, WHT tracking on vendor payments.

Brand

Brand asset library, Content calendar, Marketing campaigns, Email marketing management.

Analytics

Sales analytics, Service metrics, Team performance, Customer retention dashboards.

Operations

Incident management, Change log, On-call scheduling, Time tracking, Knowledge base.

Audit Log

Full immutable log of every create, update, delete, login, logout, and export action across all modules.

Key Features

📄E-Invoicing (Phase 1)

  • Server-side PDF generation using @react-pdf/renderer
  • Professional invoice with company header, line items, VAT, bank details
  • One-click Download PDF to browser
  • One-click Send to Client — emails PDF attachment via Resend
  • Invoice marked sentAt / sentTo on successful delivery
  • Full audit trail on every send action

🔁Subscription Auto-Invoice

  • Daily cron job scans all active subscriptions
  • Sends alerts at 60 / 30 / 7 / 1 days before expiry
  • At 7 days, automatically creates a draft renewal invoice
  • Invoice pre-filled with client name, renewal cost + 7.5% VAT
  • Deduplication prevents double invoicing per cycle

💰Payroll → PAYE Auto-Wiring

  • When HR marks payroll as fully paid, PAYE is computed automatically
  • Uses actual payroll baseSalary — not stale employee records
  • Skips employees already calculated for that period
  • PAYE records land in Tax → PAYE instantly — no manual step
  • Purple confirmation banner shown on payroll page

🔔Push + Email Notifications

  • Firebase Cloud Messaging for browser push notifications
  • Resend API for HTML email delivery with brand templates
  • Targeted by role — each notification reaches only relevant staff
  • In-app notification centre with read/unread tracking
  • Deduplication prevents repeated alerts for the same event

Root Admin Guide

The highest privilege level in Chronix OS — full unrestricted access

What Is Root Admin?

Root Admin (role: "Root Admin") is the superuser role in Chronix OS. It bypasses all permission gates — every module, every action, every record is accessible. This role is held by the platform owner and should be assigned to one or two people maximum.


In the Firestore rules, Root Admin passes the wildcard fallback rule: allow read, write: if isAuth() && isRootAdmin() — meaning no collection is off limits at the database level either.

Root Admin Capabilities

User Management

  • Create new user accounts via Admin → Users
  • Assign or change any role including assigning another Root Admin
  • Suspend or reactivate employee accounts
  • Delete user records (hard delete from Firebase Auth + Firestore)
  • Only Root Admin or System Admin can assign Root-level roles

Financial Control

  • Create, edit, approve, and delete invoices
  • Override invoice status
  • Delete unpaid invoices
  • Full access to all payments, expenses, and reports
  • Manage tax rules and rates in Firestore

System Administration

  • Access and read the full Audit Log
  • Configure push notification settings
  • Test push + email notification delivery
  • Manage all settings
  • Full access to Firestore via Firebase Console (bypasses app rules)

Data Oversight

  • View every record across all departments
  • Read all notifications regardless of targetRoles
  • Access all HR, payroll, tax, and audit data
  • Override any approval status on invoices
  • Access the Firebase Console directly for data management
How To Use Root Admin — Step by Step
1

Log In

Navigate to the Chronix OS login page. Enter your Root Admin email and password. You will be directed to the full dashboard with all 21 sidebar items visible.

2

Add New Users

Go to Settings → User Management (or the Admin Users API). Create user accounts for new staff, assign their role (e.g. HR, Staff, CFO). New users receive an invite and can log in immediately.

3

Configure Roles

If a staff member's responsibilities change, update their role in Firestore under users/{uid}.role. Their sidebar and permissions update on next login.

4

Monitor the Audit Log

Navigate to Audit Log from the sidebar. Every login, invoice action, tax computation, payroll run, and data change is recorded here with actor, timestamp, and details. Use this to investigate any discrepancies.

5

Manage Notifications

Go to Settings → Test push and email delivery. If push notifications stop working, verify FCM tokens in Firestore (users/{uid}.fcmTokens) and confirm the Firebase Admin env vars are set on Vercel.

6

Deploy Firestore Rules

When permissions are updated, run firebase deploy --only firestore:rules from the project root. Always test in the Firebase Console Rules Playground before deploying to production.

⚠ Important Security Notes for Root Admin

  • Never share Root Admin credentials. Use a strong, unique password.
  • Root Admin bypasses all UI permission checks — be deliberate with every action.
  • All Root Admin actions are captured in the Audit Log and cannot be deleted.
  • Only assign Root Admin role to individuals who absolutely require it.
  • Keep the number of Root Admin accounts to a maximum of 2.

Security Architecture

Multi-layered protection built into every part of Chronix OS

Security Layers
🔐

Layer 1 — Firebase Authentication

All users must authenticate with email + password through Firebase Auth. Session tokens (ID tokens) are short-lived JWTs signed by Google. Every API route verifies the token via the Firebase Admin SDK before processing any request. No unauthenticated request reaches any data.

🛡️

Layer 2 — Role-Based Access Control (RBAC)

Every user has a role field in Firestore. ROLE_PERMISSIONS in src/types/roles.ts defines exactly which permissions each role has. The Sidebar, all page components, and every action button check hasPermission(role, "action:module") before rendering. No UI element is shown to a role that doesn't have the required permission.

🗄️

Layer 3 — Firestore Security Rules

Database-level enforcement in firestore.rules. Even if a user bypasses the UI, Firestore rejects unauthorized reads and writes at the database level. Rules are aligned with ROLE_PERMISSIONS — e.g. HR cannot read CRM documents even with a direct Firestore query. Root Admin has a wildcard pass-through. Rules are deployed via Firebase CLI.

🌐

Layer 4 — Next.js Middleware Route Guard

Server-side middleware (src/middleware.ts) intercepts all dashboard route requests. If no valid session cookie is present, the user is redirected to the login page before any page renders. This prevents unauthenticated URL access.

🔑

Layer 5 — API Route Authentication

Every server-side API route (/api/*) requires a Bearer token in the Authorization header. The Firebase Admin SDK verifies the token and decodes the user identity. Requests without a valid token receive 401 Unauthorized immediately. Sensitive operations (PDF generation, email send) can only be triggered through these verified routes.

📝

Layer 6 — Immutable Audit Log

Every significant action — login, logout, invoice create/approve/delete, payroll run, PAYE compute, email send, expense approval, tax submission — is written to the audit_logs Firestore collection with actor UID, name, role, action, module, entity reference, and timestamp. Audit records cannot be updated or deleted (Firestore rules: allow update, delete: if false). Only Root Admin, CEO, and System Admin can read the log.

🔒

Layer 7 — Environment Variable Isolation

Firebase Admin credentials (FIREBASE_PROJECT_ID, FIREBASE_CLIENT_EMAIL, FIREBASE_PRIVATE_KEY), Resend API key (RESEND_API_KEY), and cron secret (CRON_SECRET) are stored exclusively in Vercel environment variables — never in the codebase or client-side bundles. The Admin SDK is only ever initialized in server-side API routes.

🚫

Layer 8 — Client Portal Isolation

Client-role users (external clients accessing their own data) can only read records that match their billing identity (email, company name). Firestore rules enforce userPortalBillingMatches() — a client cannot read another client's invoices, tickets, or subscription data even if they know the document ID.
