# Chronix ERP v2.0 — Reverse-Engineering Inventory (Step 1)

> **Scope of this document:** inventory only. No fixes, no PRD, no architecture doc.
> Where a finding is not directly observable in code/comments, it is explicitly marked **(inferred)**.
> Everything else is **confirmed** (read directly from source).
>
> Generated by reading every page under `src/app/(dashboard)/dashboard/*`, `src/app/portal/*`, every file in `src/lib/*` and `src/lib/accounting/*`, every API route under `src/app/api/*`, every file in `src/types/*`, and `firestore.rules`.

**Test coverage check (item 5, confirmed for the whole repo):** there is **no test framework configured at all** — no `jest.config.*`, `vitest.config.*`, `playwright.config.*`, or `cypress.config.*`, and no `test` script in `package.json` (`scripts` only has `dev`, `build`, `lint`, `typecheck`, `verify`, etc.). The only `*.test.ts`/`__tests__` files anywhere in the repo live inside `node_modules` (third-party packages' own tests). **Every module listed above has zero test coverage.** This isn't "some modules untested" — there is no testing infrastructure to begin with.

## 2–4. Per-Domain Detail: Entry Points, Inconsistent Patterns, Error-Handling Gaps

### A. Finance & Tax

**Entry points that mutate data** (`src/lib/finance-service.ts`, `expense-service.ts`, `tax-service.ts`, `invoiceCounter.ts`, `src/lib/accounting/*`):
- `createInvoice`, `updateInvoiceStatus`, `deleteInvoice`, `createPayment`, `markInvoiceSent`, `updateInvoiceApproval` (finance-service.ts)
- `createExpense`, `updateExpenseStatus`, `deleteExpense` (expense-service.ts) — **plus a second, parallel `createExpense`/`approveExpense`/`rejectExpense` in `accounting/expenses.ts`** with no state-machine guard
- Tax CRUD: `createTaxRule`/`updateTaxRule`/`toggleTaxRule`/`deleteTaxRule`, `seedDefaultTaxRules`, `createVATRecord`, `createWHTRecord`/`updateWHTCertStatus`, `createPAYERecord`, `createTaxReport` (tax-service.ts)
- Ledger: `getNextJournalNumber`, `createJournalEntry`, `voidJournalEntry` (journal-entries.ts); `createInvoiceJournalEntry`/`createPaymentJournalEntry`/`createExpenseJournalEntry`/`createPayrollJournalEntry`/`createPOJournalEntry` (auto-journal.ts); `saveVATReturn` (vat-return.ts); `runYearEndClose` (year-end.ts); `backfill*` functions + `runFullBackfill` (backfill.ts); `initializeChartOfAccounts` (chart-of-accounts.ts)
- API: `POST /api/invoices/[id]/send` (marks sent, server-side, bypasses Firestore rules via Admin SDK); `GET /api/cron/invoices` and `GET /api/cron/tax` (write reminder notifications)
- ⚠️ **`GET /api/test-invoice-counter`** — **confirmed leftover debug scaffolding shipped in production**, no auth check, permanently burns two real invoice numbers from the live counter on every hit.
- UI bypassing the service layer: `finance/invoices/[id]/page.tsx` and `tax/wht/page.tsx` both hand-write an identical inline WHT journal entry instead of calling a shared helper.

**Inconsistent patterns (confirmed unless noted):**
- **"Revenue" computed four different ways** across `finance/page.tsx`, `finance/reports/page.tsx`, `tax/corporate/page.tsx`, and the dashboard's `tax/page.tsx` — different `subtotal`/`total` fallback formulas in each.
- **"VAT collected/paid" computed three different ways**: canonical FIRS return derives it from journal-entry account codes + description keyword matching; `tax/vat/page.tsx` estimates it directly from invoices/POs (`total*0.075`); `tax/page.tsx` dashboard uses yet another PO field/status filter.
- **Two complete, divergent expense back-ends** (`expense-service.ts` vs `accounting/expenses.ts`) with different signatures and no shared state machine — the dead one has no approval guard at all.
- **PAYE bands mismatch**: the calculator (`types/tax.ts`) uses old PITA bands; the `tax/paye/page.tsx` UI *displays* new Finance-Act-2024-style bands as if that's what's computed.
- **CIT rate logic duplicated with different tiers**: `tax/corporate/page.tsx` uses a tiered rate; `tax/page.tsx`/`tax-service.ts` seed assume a flat 30%.
- **WHT journal entry hand-duplicated** in two UI files instead of going through `auto-journal.ts` like every other transaction type.
- **Account-code coverage drifts** between `auto-journal.ts`'s expense-category mapping and `profit-loss.ts`'s bucket list (e.g. `6090`/`6030`/`6080` not consistently represented in both).
- **Rules vs. code mismatch**: `firestore.rules` sets `journal_entries` update to `if false`, but `voidJournalEntry` issues an `updateDoc` — voids only succeed for Root Admin (caught by the catch-all rule), silently fail for CFO/Finance roles otherwise.
- **Rules vs. code mismatch**: Sales Reps can create invoices and post journal entries per rules, but invoice *update* (which `createInvoice` immediately performs to set `_journalPosted`) is **not** granted to Sales Rep by rules — that follow-up write is silently rejected and swallowed.

**Error handling gaps:** ~20+ swallowed `.catch(() => {})` sites (journal-error flags, audit logs, notifications all best-effort and invisible on failure); four tax dashboards use `.catch(() => [])`/`.catch(() => ({docs:[]}))` so a Firestore outage silently renders ₦0 everywhere instead of an error; multiple mutation handlers (`finance/expenses/page.tsx`, `finance/invoices/page.tsx`, `tax/wht/page.tsx`) `await` a status-changing call with **no try/catch**, so the UI optimistically flips state even when the write failed.

### B. HR / Payroll & Auth / Admin / Staff

**Entry points that mutate data** (`hr-service.ts`, `leave-service.ts`, `disciplinary-service.ts`, `auth-service.ts`, `timetrack-service.ts`, admin API routes):
- `assignEmployeeNumber`, `createEmployee`, `updateEmployee`, `addPerformanceNote`, `suspendEmployee`/`activateEmployee`, `deleteEmployee` (calls the admin DELETE route), `createPayrollRun`, `markEntryPaid`/`markAllPaid` (posts payroll journal entry)
- `createLeaveRequest`, `reviewLeave`, `cancelLeave`
- `createDiscEntry`, `resolveDiscEntry`, `addEmployeeResponse`, `updateDiscStatus`
- `signUp`, `signIn`, `sendReset`, **`createUserProfile`** (a third, apparently-unused provisioning path with no Auth account, no audit, no employee number — **inferred unused**)
- `createTimeEntry`, `amendTimeEntry` (void original + recreate)
- API: `POST /api/admin/users/create`, `DELETE /api/admin/users/[uid]` (Auth + Firestore + legacy `employees` doc), `POST /api/admin/migrate-employee-numbers`
- UI direct writes: a performance-review modal `addDoc`s straight to `performance_reviews`, bypassing any service layer.

**Inconsistent patterns (confirmed unless noted):**
- **Three different ways to provision a user** (self-signup / admin API / the orphaned `createUserProfile`), each with different side-effects and none of them aware of the others.
- **Role-gating implemented four different ways** across the domain: `hasPermission()` calls, raw `role === "CFO"` string checks, a hardcoded `Set(["HR","CEO","Root Admin","System Admin"])` in the payslip/performance API routes, and a three-way mixed check in disciplinary pages. The literal-string checks **silently fail for legacy role aliases** (e.g. `"Finance"`/`"Accountant"` for CFO) that `hasPermission`/`resolveRole` would otherwise honor.
- **Three disagreeing definitions of "who is payroll/HR staff"** between the payslip API's `MANAGER_ROLES` set (no CFO), the `payroll_runs` Firestore read rule (includes CFO, excludes CEO), and the payroll page's own `canView` check (includes CFO, excludes plain CEO) — a CEO can read payslips via the API but is denied direct `payroll_runs` reads; a CFO is the reverse.
- **Two parallel "employee record" models**: HR data now lives on `users/{uid}`, but `firestore.rules` and the delete route still reference a legacy `/employees/{uid}` collection that the service layer no longer writes to.
- **`manage:disciplinary` permission token is dead** — no code path checks it; CEO access to disciplinary records is gated by a literal `"CEO"` string instead.
- **Confirmed UI/rules mismatch**: Executive Assistant has `view:all` (so the UI shows them the "Create Review" button on the performance page), but the `performance_reviews` write rule only allows HR/CEO — their write would be silently rejected.

**Error handling gaps:** journal-posted/error flags on payroll runs swallowed (`hr-service.ts`); leave-approval/rejection notifications swallowed; several HR/leave/disciplinary handlers use `try { } finally { }` with **no `catch`**, meaning a write failure leaves the row's loading spinner stuck and never shows an error; `CreateReviewModal`'s catch discards the real error in favor of a generic "Failed to save" string.

### C. CRM, Procurement & Subscriptions (+ Client Portal)

**Entry points that mutate data** (`crm-service.ts`, `procurement-service.ts`, `subscriptions-service.ts`, `client-portal-service.ts`):
- `createLead`, `assignLead` (**inferred unused — no caller found**), `updateLeadStage`, `addLeadActivity`, `addFollowUp`/`completeFollowUp`, `updateLeadNotes` (**inferred unused**), `convertToClient` (writes both `clients` and `leads`)
- `addSubscription` (CRM-embedded)/`updateClientNotes`
- `createVendor`, `updateVendorStatus`, `addVendorRating`, `createPO`, `updatePOStatus` (posts a journal entry on "paid")
- `createSubscription`, `renewSubscription`, `cancelSubscription`, `updateSubscriptionNotes`, `toggleAutoRemind`, `setVatApplicable` — plus an **inline second renewal-invoice creation path** inside the subscription detail page itself
- `submitPortalTicket` (client portal)
- Cron: `GET /api/cron/crm` (follow-up reminders), `GET /api/cron/subscriptions` (reminders **and** auto-creates renewal invoices + journal entries)

**Inconsistent patterns (confirmed unless noted):**
- **Two unrelated "subscription" data models sharing the same word**: CRM-embedded `ClientSubscription[]` on client docs vs. the top-level `subscriptions` collection. The portal only reads the top-level collection, so anything added via the client profile page never appears to the client, and vice versa. **(Inferred unintentional.)**
- **"Cancelled" encoded two different ways**: a boolean (`cancelled: true`) on top-level subscriptions vs. an enum string (`status: "cancelled"`) on CRM-embedded ones.
- **Renewal-invoice generation duplicated** between the interactive subscription page and the cron job, with different invoice-number formats, different VAT rounding, and — critically — the manual path posts **no journal entry** and doesn't write the dedupe key, so cron and a manual renewal can both create an invoice for the same period.
- **No auto-computed renewal date** anywhere — expiry is always manual text entry.
- **Confirmed Firestore-rules mismatch**: portal reads are gated by `userPortalBillingMatches()`, which only succeeds via company-name match if the client's user doc has `portalBillingCompany` set; if unset, the fallback (`tokenEmail() == resourceBillingKey`) fails because the resource key is a company name, not an email. Any client portal user without that field set will get **permission-denied** on invoices/tickets/subscriptions despite the query succeeding client-side.
- **No UI path to cancel a Purchase Order** even though `cancelled` exists in the type — the status-advance button only marches forward through `pending → approved → delivered → paid`.

**Error handling gaps:** `ClientAuthContext`'s profile-load catch silently reduces any failure to "not a client," discarding all portal access with zero diagnostics; lead-conversion errors are fully swallowed with no message shown (and the conversion itself isn't atomic — client doc can be created while the lead update fails, leaving an inconsistent pair); numerous status-toggle handlers (`procurement/page.tsx`, `orders/page.tsx`, `subscriptions/[id]/page.tsx`) await mutations with no try/catch at all; several `logAuditEvent` calls are fire-and-forget with no `.catch`, unlike the otherwise-consistent pattern elsewhere.

### D. Projects, Tickets & Time Tracking

**Entry points that mutate data** (`projects-service.ts`, `tickets-service.ts`, `timetrack-service.ts`):
- `createProject`, `updateProjectStatus`, `addProjectActivity`, `updateTasks` (whole-array overwrite), `updateMilestones`/`completeMilestone`, `addProjectFile`/`removeProjectFile` (+ Storage), `linkProjectInvoice`, `deleteProject`
- `createTicket`, `updateTicketStatus`, `addTicketNote`, `updateClientFeedback`, `reassignTicket`, `escalateTicket` (**inferred unused — no UI caller found**)
- `createTimeEntry`, `amendTimeEntry`

**Inconsistent patterns (confirmed unless noted):**
- **Two consistency models on the same `projects` document**: tasks/milestones are whole-array overwrites (last-write-wins, no atomicity against concurrent edits) while activity/files use `arrayUnion`/`arrayRemove`.
- **Task completion never produces an activity-feed entry** even though the type system declares a `task_done` activity type — `updateTasks` only touches `tasks`/`progress`/`updatedAt`, so the feed silently omits all task events.
- **SLA dashboard's resolution/compliance metrics are dead-computed**: `resolved` is hardcoded to an empty array (`tickets/sla/page.tsx`), so average-resolution-time and compliance-rate always render as `0` / `100%` respectively, even though the comparison logic is fully written. **(Inferred unintended.)**
- **Three different "which statuses count" definitions** across the open-tickets query, the SLA page, and the main tickets list, none of which agree on whether `closed` is included.
- **ID generation for activity/note entries mixes `Date.now().toString()` and `crypto.randomUUID()`** within the *same* array across different files — a collision risk used as both React key and dedupe identity.
- **Confirmed rules/code mismatch**: the ticket partial-update rule allows a non-manager assignee to write only `["status","resolution","activity","updatedAt","resolvedAt"]`, but the actual ticket model uses a `notes` array (not `activity`) and has no `resolution` field — so `updateTicketStatus` as called by a non-manager assignee will always be rejected by rules, and the rule appears to target a schema the code no longer uses.
- **Confirmed rules/code mismatch**: the time-entry UI lets a privileged viewer "amend" *another employee's* entry, but the Firestore rule only allows the void-update when `employeeUid == auth.uid` — an admin's amend of someone else's entry will have its void step rejected while the recreate step succeeds, risking a duplicate non-voided entry.
- **One-off ad-hoc role check**: the Time page computes `canViewAll` via raw role-string equality (`role === "CFO"` etc.) mixed with one permission check, inconsistent with every other page in the domain, and broader than what the Firestore read rule actually allows (HR passes the UI check but would be denied by the rule).

**Error handling gaps:** Storage-cleanup failures during project deletion are swallowed per-file; numerous status-change/note/reassignment handlers await with no try/catch (`projects/[id]/page.tsx`, `tickets/[id]/page.tsx`); several data-loaders use `.then().finally()` with no `.catch`, so a failed read just silently renders an empty/default page instead of an error.

### E. IT Ops (Assets / Incidents / Changes / On-Call / Knowledge), Brand/Marketing, Analytics, Audit, Notifications

**Entry points that mutate data:**
- Assets: `createAsset`, `updateAsset`, `assignAsset`, `returnAsset`, `updateAssetStatus`
- Incidents: `createIncident`, `updateIncidentStatus`, `addIncidentUpdate`, `closeIncidentWithRCA`
- Changes: `createChange`, `updateChangeStatus`
- On-Call: `createOnCallSlot`, `deleteOnCallSlot`
- Knowledge: `createArticle`, `updateArticle`, `updateArticleStatus`, `incrementViewCount`
- Brand: `createBrandAsset`/`deleteBrandAsset`, `createContentPost`/`updatePostStatus`, `createCampaign`/`updateCampaignStatus`, `createEmailCampaign`/`updateEmailCampaignStatus`
- Notifications: `createNotification`, `markRead`/`markAllRead`, `notifyAssignment` + domain wrappers, `checkSubscriptionReminders`/`checkInvoiceOverdue`/`checkTaxFilingReminders`; API `POST /api/notifications/send` (the only path that also fans out to FCM push + Resend email), `POST /api/notifications/register-token`, `POST /api/notifications/test`
- Audit: `logAuditEvent` (cross-cutting, called from most of the above)
- Analytics: **no mutations** — pure reads with an in-memory cache.

**Inconsistent patterns (confirmed unless noted):**
- **Two completely separate notification-creation paths that don't share any logic**: the client-SDK `createNotification` only ever writes a Firestore doc (no push, no email), while the Admin-SDK `/api/notifications/send` route is the *only* path that actually fans out to FCM and Resend. Most in-app calls (`notifyAssignment` and its wrappers) go through the silent path.
- **Email-campaign send drops its own payload**: `brand/email/page.tsx` POSTs `customEmails`/`htmlOverride` to the send API, but that route's body schema doesn't declare those fields and instead resolves recipients by `targetRoles` and renders a fixed tax-activity template — the campaign's actual intended recipients/content are silently ignored, yet the UI still marks the campaign "sent" with a recipient count based on the emails that were never used. **(Inferred behavioral consequence from cross-reading both files.)**
- **Two independent FCM-token-write implementations** (client service vs. API route) that duplicate the same read-modify-write logic; the client-side one appears to have no caller (**inferred orphan**).
- **Hardcoded notification `type: "renewal_due"`** used for unrelated event types across the send/test routes and email-campaign send, even though a 19-value `NotificationType` enum exists and is ignored by these callers.
- **"Reject" on a change request maps to the `cancelled` status**, not a dedicated rejected state, and — unlike incidents — change-status transitions are never audit-logged at all.
- **Five different status/severity vocabularies** (incidents, changes, content posts, campaigns, email campaigns) that conceptually overlap (`draft`, `cancelled`, `completed`) but are each defined and styled independently; the email-campaigns page even redefines its own local style map instead of reusing the pattern other brand entities use.
- **Several confirmed UI-permission-gate vs. firestore.rules mismatches**: the assets list page shows action buttons to CFO that the rules don't permit; the knowledge-base and on-call rules grant write access to IT Manager that those pages' UI gates don't expose a button for; the changes-approval UI gate omits IT Manager even though the rule includes it.
- **Incidents can reach a terminal state two different ways** (`resolved` via plain status update vs. `closed` via the separate RCA-closing function) that write different field sets and log different audit actions for what is conceptually the same "incident is over" moment.

**Error handling gaps:** `logAuditEvent` is *designed* to swallow all errors silently (every audit call site therefore fails invisibly); the push/email send API logs failures to the server console only and still returns `success:true` to the caller even when push or email actually failed; numerous status-change handlers across assets/incidents/changes/on-call/knowledge/brand await mutations with no try/catch, leaving "saving…" spinners stuck on failure with no error shown; one fetch call (`fcm-client.ts`) never checks `response.ok`; the brand-email send fetch likewise never checks status before marking the campaign "sent."

## Summary of Cross-Cutting Issues (seen in 3+ domains independently)

1. **No shared "mark as paid / approved / mutate status" helper** — every domain (invoices, expenses, POs, leave, disciplinary, incidents, changes, articles) reinvents its own status-transition function with its own (often missing) guard logic, its own audit-logging discipline, and its own error handling.
2. **Two-tier mutation discipline**: some writes go through a `src/lib/*-service.ts` function; many go directly from a page component via raw `updateDoc`/`addDoc`. The service layer is not consistently the single source of truth for any domain.
3. **Silent failure is the dominant error-handling style.** Swallowed `.catch(() => {})`, empty `catch {}` blocks, and unguarded `await` inside optimistic-UI handlers appear in every single domain audited. Secondary/best-effort writes (journal entries, notifications, audit logs) are almost universally fire-and-forget with no user-visible failure signal.
4. **Firestore rules and application code were evidently written/updated independently** — at least 8 confirmed cases above where a UI button is shown (or a service function exists) that the corresponding `firestore.rules` clause would actually reject, and at least 2 cases where rules are *more* permissive than the UI exposes.
5. **Role/permission checking has at least four different idioms** in use simultaneously (`hasPermission()`, raw role-string equality, hardcoded role-name `Set`s in API routes, and three-way mixed boolean expressions), and the non-`hasPermission()` idioms don't honor legacy role aliases.
6. **Zero automated test coverage anywhere in the codebase**, and no test framework installed — every finding above has been verified only by static reading, not by running anything.
